# Spec 0001 — MacKanban MVP

Status: ready-for-agent

Vocabulary follows [GLOSSARY.md](../../GLOSSARY.md). Respects [ADR 0001](../adr/0001-capacity-and-urgency-rules.md), [ADR 0002](../adr/0002-core-data-with-code-defined-cloudkit-ready-model.md), [ADR 0003](../adr/0003-named-mackanban.md).

## Problem Statement

My to-do lists turn into dumping grounds. Adding a task costs nothing, so the list keeps growing, old tasks sink out of sight, and the list stops telling me what I'm actually going to do. I want a board that makes ageing work impossible to ignore and pushes back when I add more while nothing moves.

## Solution

MacKanban is a macOS app with one Board and three fixed Columns: Backlog, Doing and Done. Every Card shows its Urgency: it tints from neutral through amber to red as it ages (by Card Age in Backlog, by Column Age in Doing). The Board has a Capacity, the number of Open Cards it allows. Capacity rises with Throughput and falls with the Urgency of every Open Card. When Capacity is nearly used up, creating a Card first requires a Triage of the most urgent Open Card. When it is used up, creating is blocked until a Card is finished or Discarded. Doing has a strict WIP Limit. A menu bar extra shows the Board's state at a glance.

## User Stories

### Board and Cards

1. As a user, I want one Board with the fixed Columns Backlog, Doing and Done, so that there is nothing to configure.
2. As a user, I want to create a Card with a title and optional notes, so that I can capture work quickly.
3. As a user, I want every new Card to start in Backlog, so that starting work is always a deliberate second step.
4. As a user, I want to edit a Card's title and notes while it is in Backlog or Doing, so that I can sharpen it as I learn more.
5. As a user, I want editing a Card never to change its ages, so that renaming can't make old work look new.
6. As a user, I want Done Cards to be read-only, so that finished work stays as it was.
7. As a user, I want to move a Card from Backlog to Doing, from Doing to Done, and from Doing back to Backlog, by drag and drop or by keyboard, so that the Board reflects what I'm doing.
8. As a user, I want nothing to move out of Done, so that finishing is a real commitment.
8a. As a user, I want every Card to pass through Doing on its way to Done, so that finishing always means having started.
9. As a user, I want ⌘Z right after a move, Discard or creation to undo it, so that a slip of the mouse costs nothing.
10. As a user, I want an undone move to restore the Card's previous Column Visit instead of starting a new one, so that undo can't reset a Card's ages.
11. As a user, I want to Discard an Open Card, so that I can honestly drop work I'll never do.
12. As a user, I want Discarded Cards not to count as Throughput, so that dropping work doesn't earn the same as finishing it.
13. As a user, I want Backlog sorted oldest first and Doing sorted by Column Age, longest first, with no manual reordering, so that old work can't be hidden at the bottom.
14. As a user, I want Done sorted newest first, so that I see what I just finished.
15. As a user, I want Done Cards to leave the Board 7 days after entering Done and go to the Archive, so that Done doesn't grow forever.
16. As a user, I want a read-only Archive window (⌘⇧A) listing archived Done Cards and Discarded Cards with their dates, so that I can look back.

### Urgency

17. As a user, I want each Backlog Card's background tinted from neutral through amber to red based on its Card Age (neutral up to 3 days, full red at 21), so that I can see what's rotting.
18. As a user, I want each Doing Card tinted based on its Column Age (neutral up to 1 day, full red at 7), so that I can see what's stuck.
19. As a user, I want Column Age to add up across visits, so that bouncing a Card between Doing and Backlog doesn't reset it.
20. As a user, I want every Open Card to show its age as a label ("12d" in Backlog, "4d in Doing" in Doing), so that Urgency doesn't rely on colour alone.
21. As a user, I want Done Cards to show no Urgency, so that finished work looks calm.
22. As a user, I want the tints to work in both light and dark mode, so that the signal is readable in either.

### WIP Limit

23. As a user, I want to set the WIP Limit for Doing (1–5, default 3) in Settings, so that it fits how I work.
24. As a user, I want moving a Card into Doing to be refused when Doing is at the WIP Limit, so that I finish before I start.
25. As a user, I want lowering the WIP Limit below the current number of Doing Cards to be allowed, with the Doing header showing "3 / 2" in red and new starts blocked, so that nothing gets bounced automatically.

### Capacity, Triage and creating Cards

26. As a user, I want Capacity computed as 5 + Throughput − Σ Urgency of all Open Cards, rounded down, capped at 20, with no floor, so that the room for new work follows how I actually work.
27. As a user, I want a Capacity gauge next to the New Card button showing used and total Capacity, so that I know how much room is left.
28. As a user, I want the gauge to explain what makes up Capacity (base, +Throughput, −aging), so that a drop is never a mystery.
29. As a user, I want Capacity to update while the app is open, so that it reflects ageing in real time.
30. As a user, I want ⌘N in the Board window and New Card… in the menu bar extra to open the New Card sheet, so that I can create a Card from either place.
31. As a user, I want a Triage step before the title field when 2 or fewer slots remain or any Open Card is fully red, so that I face my most urgent Card before adding another.
32. As a user, I want Triage to show the Open Card with the highest Urgency and let me start it, Discard it or keep it, so that the friction leads to a decision.
33. As a user, I want "start" in Triage to be unavailable, with the reason shown, when Doing is at the WIP Limit, so that Triage can't break the WIP Limit.
34. As a user, I want keeping a Card in Triage not to change its Urgency, so that Triage is not a snooze button.
35. As a user, I want the sheet to explain the block when Capacity is used up ("Capacity 7, Open Cards 9: finish or Discard 3 Cards") and offer no way to create, so that the rule is clear and firm.

### Menu bar extra and app

36. As a user, I want MacKanban to be a regular app with a Dock icon and a Board window, so that I can ⌘Tab to the Board.
37. As a user, I want a menu bar icon tinted by the highest Urgency on the Board, and shown in a filled variant when Capacity is used up, so that I see the Board's state without opening it.
38. As a user, I want the menu bar menu to show the Capacity line, the Doing Cards (choosing one moves it to Done), New Card…, Open Board, Settings… and Quit, so that I can do the everyday actions without the window.
39. As a user, I want a Launch at login toggle in Settings (off by default), so that the menu bar extra can be there from startup.
40. As a user, I want my Board saved automatically after every change, so that there is nothing to save.
41. As a user, I want MacKanban to follow the system's light and dark appearance, so that it fits my desktop.

## Implementation Decisions

- **Stack:** Swift 6, AppKit-first. SwiftUI only where it helps (Settings, possibly the Card view and sheets), hosted in AppKit via `NSHostingView`. macOS 14+. A regular app (Dock icon, no `LSUIElement`) plus an `NSStatusItem`. Built with SwiftPM, no Xcode. As in MacJot, a bundle script produces an ad-hoc-signed app and an install script copies it to the user's Applications folder and restarts it. Bundle ID `com.onethingwell.mackanban`. No third-party dependencies.
- **Module split:** `KanbanCore` (Foundation and Core Data, no AppKit) holds every rule. The `MacKanban` app target only wires UI events to the core and renders its state.
- **Core: rules** (pure functions, no storage, internal to the core and only reachable through Board):
  - Urgency(Card, now) → 0…1, using a grace period and a linear ramp, with Card Age for Backlog and accumulated Column Age for Doing (ADR 0001).
  - Throughput(Cards, now) → number of Cards whose Done visit started within the last 14 days.
  - Capacity(Cards, now) → the value plus its breakdown (base, Throughput, aging penalty) for the gauge.
  - Creation gate(Cards, now) → `open`, `triage(card)` or `blocked(capacity, openCount)`.
  - Archive check(Card, now) → whether a Done Card's Done visit is older than 7 days.
- **Core: Board** is the single facade the app uses. Its operations are create, edit, move, Discard, keep (a no-op that exists so Triage reads clearly) and revert last change (for undo), plus queries for Column contents in display order (each Card with its Urgency and the age its label shows), Capacity with breakdown, the creation gate, the Archive and WIP status. It enforces the allowed moves, the WIP Limit, read-only Done, and the gate on create. It throws typed errors that the app turns into messages.
- **Core: store:** Core Data through `NSPersistentContainer` with the model built in code (ADR 0002). It has two entities. `Card` has an id, title, notes, created date and discarded date. `ColumnVisit` has a column, entered and left (null while current), and a card. All attributes are optional or have defaults, there are no unique constraints, and relationships are optional with inverses. The `NSPersistentCloudKitContainer` swap happens later.
- **Undo:** the app registers inverse operations with `NSUndoManager`. Undoing a move calls the Board's revert operation, which deletes the latest Column Visit and reopens the previous one (sets its `left` back to null) instead of adding a new visit.
- **Dependencies injected into Board:** the clock, the persistent container (SQLite on disk in the app, in-memory in tests) and the WIP Limit. Nothing else.
- **Time:** all ages use wall-clock time. The app re-renders Urgency, the gauge and the menu bar icon on a timer (once a minute) and after every change.
- **Settings:** WIP Limit (1–5) and Launch at login (`SMAppService`). Stored in `UserDefaults`, not in the Board store.
- **Defaults:** WIP Limit 3; Launch at login off. The Capacity base (5), cap (20), 14-day Throughput window, 7-day Archive delay, Urgency thresholds and the Triage trigger (2 or fewer free slots) are constants in `KanbanCore`, not settings (ADR 0001).

## Testing Decisions

- **Good tests** only exercise external behaviour: they give inputs at a seam and assert on what comes back. They don't assert on private state, call order or Core Data internals, and they should survive a refactor of the internals.
- **One seam: Board.** All tests construct the Board over an in-memory Core Data store with an injected clock they can advance, and assert only on what the Board's queries return. The Urgency, Throughput, Capacity, gate and Archive functions are internal details. They're covered through Board scenarios, not tested directly, so the formula can be refactored freely.
- **Rule scenarios** (e.g. "create a Card, advance 12 days, expect Urgency 0.5"). Cases that must pass:
  - A Backlog Card 3 days old has Urgency 0, 12 days old 0.5, and 30 days old 1.
  - A Card that is 30 days old but has been in Doing for 1 day has Urgency 0.
  - Doing for 3 days, back to Backlog, then Doing for 2 more days gives a Column Age of 5 days.
  - A new Board with no Cards has Capacity 5.
  - 4 Cards Done in the last 14 days and one done 15 days ago gives Throughput 4.
  - Open Cards with Urgency 1, 0.5 and 0.4 and Throughput 2 give Capacity ⌊5 + 2 − 1.9⌋ = 5.
  - Capacity is capped at 20 and can go to 0 or below.
  - A Discarded Card adds nothing to Throughput and no Urgency.
  - The gate is `open` with 3 or more free slots and no fully red Card, `triage` with 2 free slots or with any fully red Card, and `blocked` with 0 or fewer free slots. Triage picks the Card with the highest Urgency.
- **Board behaviour scenarios.** Covers:
  - Allowed and refused moves, including out of Done and Backlog → Done.
  - The WIP Limit, including after lowering it.
  - Edits not touching ages, and Done being read-only.
  - Discard.
  - Revert restoring the previous visit without a new one.
  - Display order per Column.
  - The Archive after 7 days.
  - Create being refused when blocked.
  - Data surviving a reload of the container (run once against a temporary SQLite file).
- **Not automated:** the AppKit shell is verified by hand against this checklist:
  - Drag and drop and keyboard moves.
  - Tints in light and dark mode.
  - Gauge breakdown.
  - Triage sheet paths (start, Discard, keep, start unavailable).
  - Blocked sheet.
  - Menu bar icon states and menu actions.
  - ⌘Z after each kind of change.
  - Launch at login.
  - The Archive window.
- **Tooling:** Swift Testing, run through a test script as in MacJot (it works around the Command Line Tools limitation). Build and test commands need the Claude Code sandbox disabled.
- **Prior art:** none in this repository yet. MacJot's `JotCoreTests` show the patterns to follow: a core library tested at its facade over real storage with an injected clock.

## Out of Scope

Anything not in the user stories. Specifically, for this MVP:
- Manual reordering or a "planning order".
- Global hotkey.
- Notifications.
- iCloud sync.
- Multiple Boards.
- Custom Columns.
- Due dates, priorities and tags.
- Stats dashboard.

The first three and sync go to the Later section of `BACKLOG.md`.

## Further Notes

- **Build order** (each milestone ends in something runnable):
  1. **Skeleton:** the SwiftPM package with `KanbanCore` and the app target, scripts, a Dock app with an empty Board window and a status item.
  2. **Store and Board:** code-defined model, Board facade, moves, WIP Limit, Discard, revert (behaviour scenarios).
  3. **Rules:** Urgency, Throughput, Capacity, creation gate, Archive, exposed through Board queries (rule scenarios).
  4. **Board window:** three Columns, Card views with tints and age labels, drag and drop, keyboard moves, undo.
  5. **Creating Cards:** the New Card sheet with Triage and the blocked state, the Capacity gauge.
  6. **Menu bar extra:** icon states and menu.
  7. **Archive and Settings:** Archive window, WIP Limit, Launch at login.
- **Throughput farming is accepted** (ADR 0001): creating and immediately finishing trivial Cards raises Capacity, up to the cap of 20. There's no guard against it.
